# LH-V1.5-C03 — Deterministic Memory Laboratory

**Status:** Approved for implementation planning  
**Date:** 2026-08-17  
**Campaign:** LH-V1.5-C03  
**Base:** `main` after LH-V1.5-C02 merge commit `5f0839f1eede4ae333e8c6da77b10752a6b4eb6c`

## 1. Purpose

LH-V1.5-C03 builds a trustworthy, deterministic memory laboratory for Lighthouse.

Its sole purpose is to prove that the existing C01/C02 memory path remains correct under sustained automated use:

```text
conversation
→ deterministic turn journal
→ CaseMemoryCandidate
→ candidate fingerprint
→ test-only Operator simulation
→ normal C02 promotion service
→ promotion audit
→ isolated curated CaseMemory
→ deterministic retrieval
→ invariant checks
```

C03 does **not** add case lifecycle mutation. Resolution, reopening, archival, editing, consolidation, semantic deduplication, or model-driven memory management belong to later campaigns after the laboratory itself has been proven trustworthy.

## 2. Authority model

C03 must preserve the production C02 authority boundary.

The laboratory may automate Operator actions only inside isolated validation infrastructure. It must not introduce a production auto-approval path.

The test-only Operator simulator may:

- request a real C01 candidate preview,
- read the exact fingerprint generated by Lighthouse,
- submit that exact fingerprint to the existing C02 promotion API,
- intentionally replay, stale, or withhold approval according to the scripted scenario.

It may not:

- call `save_case_memory()` directly,
- append directly to `cases.jsonl`,
- bypass `promote_case_memory_candidate()`,
- grant itself generic memory-policy authority,
- invoke a model, tool executor, subprocess, or OS mutation as part of memory approval.

Production trust remains:

> Only explicit Operator approval of the exact current candidate contents may authorize turn-derived CaseMemory persistence.

C03 automation is validation infrastructure, not production authority.

## 3. Deterministic-only execution envelope

Formal C03 campaigns run with:

- LLM/Ollama calls disabled,
- model route authority disabled,
- tool execution disabled,
- subprocess/OS command execution forbidden,
- Windows mutation forbidden,
- generic memory-policy approval forbidden,
- all operational and curated memory redirected to isolated campaign directories.

The laboratory tests Lighthouse's deterministic substrate only.

## 4. Components

### 4.1 `memory_lab.py`

A reusable orchestration service that:

1. receives a deterministic scenario,
2. drives the real Lighthouse services in production order,
3. records pre/post store and audit state,
4. performs expected Operator simulation,
5. invokes real C02 promotion where applicable,
6. invokes real deterministic retrieval where applicable,
7. evaluates trust invariants,
8. emits one `MemoryLabCycleResult`.

The laboratory service must never write curated memory directly during the measured action under test.

### 4.2 `memory_lab_scenarios.py`

Owns deterministic scenario generation.

Scenario selection must be reproducible from:

- C03 scenario schema/version,
- campaign seed,
- cycle index,
- fixed scenario-family quotas.

The generator returns scripted inputs and expected outcomes; it does not perform persistence.

### 4.3 Test-only Operator simulator

A deliberately narrow helper used by the laboratory.

For scenarios that require approval, it reads the current valid candidate fingerprint from the real preview and submits it through `promote_case_memory_candidate()`.

For stale scenarios it deliberately submits an old fingerprint after evidence changes.

It receives no direct low-level store writer.

### 4.4 Isolated fixture/precondition builder

Some negative scenarios require pre-existing state that cannot be produced by the normal C02 authority path without changing the thing being tested. The canonical example is a same-`case_id`, different-content conflict.

A dedicated test-only fixture builder may seed **isolated campaign directories only** before the measured cycle begins.

Rules:

- fixture writes are allowed only for explicit scenario preconditions,
- fixture writes must never target normal Lighthouse operational or curated memory,
- the fixture builder is not available to the test Operator simulator,
- the measured promotion action must still pass through the real C02 promotion service,
- every seeded case/record is declared in the scenario and recorded in cycle evidence,
- fixture writes are excluded from `case_write_performed` for the measured action but included in before/after physical store counts,
- fixture seeding must not be used for ordinary promotion, duplicate replay, or stale-approval scenarios where the real production path can create the required state.

Controlled failure scenarios may also install test-only dependency failures at named C02 boundaries (for example audit append or curated save). Each injected failure must be declared in scenario evidence. These injections test C02 failure semantics; they do not create production failure controls.

This fixture boundary exists only to construct adversarial preconditions. It does not relax production persistence authority.

### 4.5 Campaign runner

A developer-only runner, expected shape:

```text
python scripts/run_memory_lab.py --cycles 50 --seed 20260817
python scripts/run_memory_lab.py --cycles 250 --seed 20260817
python scripts/run_memory_lab.py --cycles 1000 --seed 20260817 --fail-fast
```

Useful limited options may include:

- `--cycles`
- `--seed`
- `--fail-fast`
- `--scenario-summary`
- `--evidence-dir`

Scenario distributions and trust invariants are versioned C03 policy, not arbitrary CLI knobs.

No normal Lighthouse production command for automatic case approval is added in C03.

## 5. Campaign isolation and evidence

Each campaign receives a self-contained directory outside normal Lighthouse operational/curated memory:

```text
<campaign>/
    campaign_manifest.json
    cycle_results.jsonl
    campaign_summary.json
    operational/
        conversation_turns.jsonl
        conversation_turn_feedback.jsonl
        case_promotions.jsonl
    curated/
        cases.jsonl
```

Generated campaign evidence is validation evidence and must not be committed to Git.

The manifest records at minimum:

- C03 schema/version,
- git commit,
- Python version,
- seed,
- requested cycle count,
- scenario-family quotas,
- fail-fast mode,
- model-disabled state,
- campaign start timestamp.

The summary records the final observable campaign state.

## 6. Scenario families

Formal C03 campaigns exercise six families.

### 6.1 Normal promotion

Valid deterministic turn → valid candidate → exact approval → one curated case.

Assertions include:

- promotion decision is `promoted`,
- one and only one physical case write occurs,
- audit attempt precedes promoted outcome,
- persisted case is equivalent to the approved proposed case.

### 6.2 Idempotent replay

Exact approval repeated for an already-persisted equivalent case.

Assertions include:

- decision is `duplicate`,
- `persisted=True`,
- `case_write_performed=False`,
- physical curated case count does not increase,
- duplicate attempt/outcome audit is present.

The pre-existing equivalent case for this family must be created through the real C02 path, not fixture seeding.

### 6.3 Stale evidence

Preview candidate → introduce deterministic Operator feedback/evidence change → submit old fingerprint.

Assertions include:

- old fingerprint is refused,
- no curated write occurs,
- refusal happens before the persistence/audit gate,
- re-preview produces a different fingerprint for the same candidate lineage when the fingerprint-bound evidence changed.

### 6.4 Conflict protection

A fixture precondition creates one isolated stored case whose `case_id` matches the candidate but whose meaningful CaseMemory content differs. The measured action then submits the exact current candidate through the real C02 promotion gate.

Assertions include:

- decision is `conflict`,
- no overwrite occurs,
- no second conflicting physical record is appended,
- audit truth matches store truth.

### 6.5 Retrieval discrimination

Populate isolated curated memory with controlled relevant and irrelevant cases, then query through the real memory retriever.

Where the cases under test can be created through normal C02 promotion, that path is preferred. Fixture seeding is allowed only for retrieval-specific preconditions that are explicitly declared and are not themselves being used to test promotion correctness.

Assertions include:

- designated relevant case appears within the configured deterministic retrieval window,
- designated irrelevant/similar cases do not outrank the expected relevant case when scenario terms distinguish them,
- retrieval remains read-only and non-authoritative.

### 6.6 Controlled failure integrity

Install a declared test-only failure at a named persistence/audit dependency, then drive the measured approval through the real C02 service.

Assertions include C02 truth semantics:

- attempt-audit failure blocks curated write,
- curated-save failure reports error and records outcome when possible,
- post-write outcome-audit failure reports `partial/promoted`, preserves the persisted case, and does not roll back,
- retry after a post-write partial result resolves as duplicate without a second curated write.

## 7. Scenario distribution

Formal campaigns use fixed quotas so edge cases cannot disappear through random sampling.

The canonical family ordering is:

1. normal promotion,
2. duplicate replay,
3. stale evidence,
4. conflict protection,
5. retrieval discrimination,
6. controlled failure integrity.

### 7.1 50-cycle smoke quotas

- 20 normal promotion cycles,
- 10 duplicate replay cycles,
- 8 stale-evidence cycles,
- 5 conflict cycles,
- 5 retrieval-discrimination cycles,
- 2 controlled failure-injection cycles.

Total: 50 cycles.

### 7.2 250-cycle validation quotas

- 100 normal promotion cycles,
- 50 duplicate replay cycles,
- 38 stale-evidence cycles,
- 25 conflict cycles,
- 25 retrieval-discrimination cycles,
- 12 controlled failure-injection cycles.

Total: 250 cycles.

### 7.3 1,000-cycle acceptance quotas

- 400 normal promotion cycles,
- 200 duplicate replay cycles,
- 150 stale-evidence cycles,
- 100 conflict cycles,
- 100 retrieval-discrimination cycles,
- 50 controlled failure-injection cycles.

Total: 1,000 cycles.

Development runs of 1–10 cycles use a deterministic round-robin over the canonical family ordering and are not formal acceptance evidence.

The seed determines the deterministic order and scenario details within the applicable quota set. The same C03 version + seed + formal cycle count must reproduce the same logical campaign expectations.

Production-required timestamps/UUIDs need not be byte-identical across runs; expected decisions, scenario inputs, case-domain content, fixture declarations, and invariant outcomes must be reproducible.

## 8. Cycle result contract

Each cycle emits a stable `MemoryLabCycleResult` containing enough observable state to explain its outcome.

Minimum fields:

1. schema_version
2. campaign_id
3. seed
4. cycle_index
5. scenario_family
6. scenario_id
7. source_turn_id
8. candidate_id
9. candidate_fingerprints
10. fixture_case_ids
11. injected_failure
12. expected_decision
13. actual_decision
14. expected_persisted
15. actual_persisted
16. case_count_before
17. case_count_after
18. audit_count_before
19. audit_count_after
20. retrieval_expected_case_id
21. retrieval_observed_case_ids
22. passed
23. errors
24. warnings

The contract must capture facts rather than infer success from a service status alone.

Example: a `duplicate` decision passes only if the curated physical case count also remains unchanged.

## 9. Campaign result contract

`MemoryLabCampaignResult` records at minimum:

- schema_version,
- campaign_id,
- seed,
- requested_cycles,
- completed_cycles,
- scenario quotas and completed distribution,
- passed_cycles,
- failed_cycles,
- curated_case_count,
- fixture_write_count,
- promotion attempt/outcome counts,
- stale refusals,
- duplicate decisions,
- conflict decisions,
- injected failures,
- retrieval checks passed/total,
- unexpected writes,
- physical duplicate count,
- conflict overwrite count,
- audit inconsistency count,
- forbidden authority crossing count,
- start/end timestamps,
- final status,
- errors/warnings.

Final status is one of:

- `green` — all requested cycles completed and every invariant held,
- `failed` — one or more invariants were violated,
- `aborted` — infrastructure/harness failure prevented a trustworthy conclusion.

The formal C03 acceptance campaign has no yellow/partial-success state.

## 10. Hard invariants

A formal campaign requires:

- zero unexpected curated case writes during measured actions,
- zero undeclared fixture writes,
- zero stale approvals accepted,
- zero physical duplicate cases except explicitly declared fixture state that is itself under a corruption-detection test,
- zero conflict overwrites,
- 100% expected promotion-audit consistency,
- 100% required retrieval assertions,
- zero forbidden model/tool/OS/generic-policy authority crossings,
- all completed cycles individually explainable from recorded evidence.

Expected `refused`, `duplicate`, `conflict`, `error`, or `partial` outcomes may be passing cycles when they exactly match the scenario and underlying store/audit truth.

## 11. Stop conditions

### 11.1 Immediate trust-boundary stop

Formal campaigns stop immediately on:

- unexpected curated persistence during a measured action,
- undeclared fixture persistence,
- stale fingerprint accepted,
- forbidden model/tool/OS/generic-policy call,
- corrupted/unreadable campaign store where truth cannot be established,
- physical duplicate record violating idempotency,
- conflicting record overwrite/second append,
- audit state contradicting confirmed store state.

### 11.2 Ordinary scenario assertion failure

Small development campaigns may optionally continue after ordinary assertion mismatches to collect examples.

The formal 1,000-cycle acceptance run is fail-fast for trust-boundary violations and ultimately GREEN only if every required invariant passes.

## 12. Harness validation strategy

The laboratory must prove that it can detect defects before its soak result is trusted.

Required harness tests include:

- same seed/version produces repeatable logical scenario sequence,
- 50/250/1,000 formal family quotas are exact,
- test Operator cannot bypass C02 persistence,
- fixture builder cannot target non-campaign memory paths,
- fixture activity is declared and distinguishable from measured action writes,
- each scenario family detects an intentionally introduced mismatch,
- unexpected-write detector fails a corrupted scenario,
- stale-acceptance detector fails when stale persistence is forced,
- physical-duplicate detector identifies duplicate rows,
- audit mismatch detector identifies inconsistent journal/store truth,
- forbidden model/tool/OS/generic-policy calls are trapped,
- campaign manifest contains sufficient replay configuration,
- deliberately corrupted campaign state cannot report `green`.

Negative harness tests are mandatory.

## 13. Run ladder

C03 uses the following staged validation ladder:

```text
Development gate        1–10 cycles
Smoke campaign              50 cycles
Validation campaign        250 cycles
Primary acceptance       1,000 cycles
Optional durability      5,000 cycles
```

The 5,000-cycle durability run does not block C03 completion. If run, it uses a separately versioned quota policy derived from the accepted C03 family distribution rather than silently reusing an unspecified allocation.

## 15. Explicit exclusions

C03 does not add:

- case resolution,
- case reopening,
- case archival,
- case editing,
- case consolidation,
- semantic deduplication,
- automatic production promotion,
- background memory management,
- LLM memory reasoning,
- model-assisted retrieval,
- tool execution,
- Windows actions,
- production auto-approval.

C03 does not change the CaseMemory epistemic meaning established in C01/C02.

## 16. Architectural outcome

C03 should leave Lighthouse with a reusable deterministic proving ground for memory behavior.

The milestone is deliberately infrastructure-first:

> Prove the memory laboratory before teaching Lighthouse to mutate memory lifecycle state.

If the 1,000-cycle acceptance campaign is green, later lifecycle work can be introduced against a validation rig whose own trustworthiness has already been demonstrated.
